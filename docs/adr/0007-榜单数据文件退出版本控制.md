# ADR-0007：榜单数据文件退出版本控制

- 状态：已接受（CI 数据基准部分已由 ADR-0014 取代）
- 日期：2026-10-19
- 决策人：owner（「这种数据通常都是走接口，哪有加入 git 的道理」→ 确认两个文件都不跟踪）

## 背景

`data/snapshot.json`（三榜聚合缓存）与 `data/history.json`（历史档案）随仓库初始化
提交进入 git，此后本地服务每次定时刷新都会改写这两个文件，产生一串
`chore: 数据快照例行刷新` 提交——后经 owner 确认，这些提交是未留神产生的，不是要
维护的惯例。

两个文件性质不同：

| 文件            | 性质                         | 可否重建         |
| --------------- | ---------------------------- | ---------------- |
| `snapshot.json` | 当前三榜状态的聚合缓存       | 可，随时重新抓取 |
| `history.json`  | 逐次抓取 diff 沉淀的历史档案 | 不可，上游不提供 |

数据本就「走接口」：服务端定时从三站摄取（ADR-0006、ADR-0008），这两个文件只是摄取
层与页面之间的落地缓存。把它纳入版本控制带来三类持续成本：拉取冲突（本地刷新与远程
刷新必打）、审查噪声（动辄上千行 diff）、数据变更与代码变更混在同一历史里。

## 决策

两个文件都退出 git：`git rm --cached` 保留磁盘文件，`.gitignore` 登记；此后的刷新
只落磁盘、不进提交。摄取契约不变（服务启动/刷新时写盘，页面经 `/api/data` 读取）。

配套改造：

- CI：E2E 此前隐式依赖「提交进仓库的快照」（断网也能过）。改为构建后、启服务前
  显式执行 `npm run refresh` 落数据，失败即步骤失败并给出明确信号，不再有隐式基准。
- 文档：README 与 handoff.md 中「随交付附带的快照」「例行刷新以 `chore:` 提交」等
  表述同步更正。

## 后果

- 仓库历史只剩代码与文档；数据刷新不再产生提交与拉取冲突。
- CI 门禁从「读仓库快照」变为「实时抓取」：网络不通时工作流会红（原先源站标 stale
  后 E2E 仍绿）。这是刻意的取舍——门禁应当反映摄取链路的真实状态。AA 单站约
  14–21 秒，三站合计仍在 15 分钟预算内。
- 新克隆冷启动有一段空榜期：`loadState()` 对缺失文件静默，启动即监听，
  `refreshDue()` 触发后台刷新，三站抓完（约半分钟）前页面无数据。
- `history.json` 不再跨克隆保留：现有档案已备份到仓库外，新克隆的历史从零积累。
  若将来需要可迁移的历史，应导出为数据文件随需分发，而非提交进 git。
- 本地开发机上两个文件从「被跟踪」变为「被忽略」，`git status` 不再因刷新变脏，
  也不必再为数据改动 stash / skip-worktree。

## 后续修订

- 2026-10-20（ADR-0014）：CI 不再执行 `npm run refresh`，E2E 改用仓库内确定性夹具与临时 `FRONTIER_DATA_DIR`。`data/` 两个文件仍不进版本控制；真实源站抓取改由独立的 `source-health` 定时工作流巡检。本文其余决策不变。
- 2026-11-14（ADR-0014 修订）：`source-health` 定时巡检工作流已移除，源站健康的观察回归 owner 本地日常刷新（启动即全量刷新 / `npm run refresh`）。本文其余决策不变。
