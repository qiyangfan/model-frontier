# ADR-0014：CI 使用确定性夹具，源站健康独立巡检

- 状态：已接受
- 日期：2026-10-20
- 决策人：owner（「CI 不应该绑定外网」）与实现决策

## 背景

ADR-0007 为避免隐式依赖仓库快照，把 CI 改成构建后执行 `npm run refresh`、再跑三套 E2E。实际后果是每次 push / PR 的通过与否取决于四个外部站点的可用性、限流与解析契约。源站抓取本身就是项目最不稳定的部分（ADR-0006、0008、0013 都是适配器维护），把它的短期波动绑到代码门禁上，会让与改动无关的 CI 变红，也会稀释真正的行为回归信号。

E2E 断言的是页面行为（图表交互、门户六页、证据与历史流），不是「源站今天是否在线」；适配器解析由单测覆盖，源站契约漂移需要的是可观测的巡检信号，而不是阻塞合并。

## 决策

- CI 的 E2E 使用仓库内固定夹具 `tests/fixtures/snapshot.json`。运行前由 `tests/prepare-fixture.mjs` 把缓存时间归一化到当前时刻、写入临时 `FRONTIER_DATA_DIR`，并以 `FRONTIER_AUTO_REFRESH=0` 启动服务，确保门禁不发出任何源站请求。
- 真实源站抓取由独立的 `.github/workflows/source-health.yml` 每日定时（另支持手动触发）执行 `npm run refresh`；失败只标记巡检工作流，不阻塞代码门禁。
- ADR-0007 中「CI 显式刷新真实数据」的条款和 ADR-0004 中「三套 E2E 留在本地」的 CI 范围描述，均以本 ADR 为准。

## 备选方案

- **保持实时刷新**：实现最简单，但每次代码评审都被四站网络与解析状态绑架；一次源站超时就会产生与改动无关的红灯，CI 时长也受源站影响。已否决。
- **在 CI 内 mock HTTP**：需要为四套适配器维护抓取层替身，替身与真实响应结构漂移时测试会失真；夹具落在项目已有的 `FRONTIER_DATA_DIR` 抽象上，改动更小、路径更接近真实启动流程。
- **E2E 改用合成数据**：要重新构造几百个模型与成本/开放状态组合才能覆盖现有断言，维护成本高且失真；固定真实快照更可靠。

## 后果

- CI 可在不访问源站、无需源站凭据的环境中稳定运行；E2E 结果只反映代码行为。
- E2E 不再验证源站解析契约。该风险由适配器单测与每日 `source-health` 巡检覆盖，漂移发现延迟最长约一天。
- 夹具是一次性真实快照，数据内容不随上游变化。页面行为断言若依赖新模型或新来源字段，需要手动更新夹具：一次成功刷新后把 `data/snapshot.json` 覆盖到 `tests/fixtures/snapshot.json`。
- `FRONTIER_AUTO_REFRESH=0` 是服务端的自动抓取开关，默认开启；仅用于确定性测试与离线演示，不影响手动刷新接口。
- 本决策不改变评分口径、分享链接或用户可见的数据语义。

## 修订记录

- 2026-11-14：**移除 `.github/workflows/source-health.yml`，每日定时巡检下线（owner 指示「干掉它」）**。理由：①巡检信号没有消费者——单 owner 本地工具，GitHub 上的失败标记没有告警通道，等于无人看；②漂移发现走本地反而更快——owner 每日启动服务即触发全量刷新（ADR-0014 决策时尚未存在的「启动即刷新」语义），源站失配在本地第一时间暴露，云端巡检「最长一天」的发现延迟只会更慢；③GitHub Actions 此前处于 billing 锁定状态，该工作流从未成功运行，红灯纯噪音。「门禁走确定性夹具、不绑源站」的核心决策不变；源站契约漂移的覆盖责任回归适配器单测与本地日常刷新。ADR-0007 的「后续修订」同步补记。
